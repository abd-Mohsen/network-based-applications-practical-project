# RideFlow — شرح المشروع بالعربية

هذا الملف يشرح نظام **RideFlow** بالكامل: ما الهدف منه، كيف يعمل، وكيف يرتبط كل جزء فيه بمحاضرة «التكامل والتشغيل البيني» (المحاضرة السابعة، عملي التطبيقات الشبكية الموزّعة، جامعة دمشق). الواجهة الرسومية نفسها (على المنفذ 8080) تبدأ بالعربية (من اليمين إلى اليسار) افتراضياً، وفيها مفتاح تبديل EN/ع أعلى كل صفحة يتذكّره المتصفّح — هذا الملف هو الشرح الموسّع لما تراه فيها.

## الفكرة بإيجاز

لا يوجد نظام مؤسساتي يعيش وحده (شريحة 3). قيمة أي نظام تأتي من الأنظمة التي يتحدّث إليها، والحدود بين الأنظمة هي حيث تتركّز معظم الأعطال. بدل أن نقرأ هذه الفكرة فقط، بنينا نظاماً صغيراً بنكهة تطبيقات حجز الرحلات (أشبه بأوبر) ليست وظيفته محاكاة شركة نقل، بل **إظهار كل مفهوم من المحاضرة على أرض الواقع**، بحيث يمكنك أن تُعطِّل أي وصلة فيه عمداً وتقيس ما يحدث للمعطيات بالأرقام الحقيقية — وهذا بالضبط ما يطلبه البحث العملي في الشريحة الأخيرة من المحاضرة.

النظام ليس تطبيق حجز رحلات كامل عمداً: سبع خدمات صغيرة فقط، كل واحدة منها تُجسِّد مفهوماً محدداً من المحاضرة.

## البنية المعمارية

```
المتصفح (الراكب/السائق) → web (واجهة + BFF، المنفذ 8080)
                                │ كتابات: عبر gateway
                                │ قراءات: استطلاع مباشر لباقي الخدمات
                                ▼
                            gateway (JWT · تحديد معدّل) ──proxy──▶ trip-service
                                                                      │
                                                    مطلوبة ─accept─▶ مقبولة ─complete─▶ مكتملة
                                                                      │ ينشر trip.completed (outbox)
                                                                      ▼
                                                             طابور RabbitMQ ──(نفاد المحاولات)──▶ trip.completed.dlq
                                                                      │ استهلاك
                                                                      ▼
                                           payment-service ⇄ fraud-check-service
                                           (عدم تكرار الأثر ·      (خدمة متزامنة هشّة،
                                            إعادة محاولة + قاطع)      قابلة للتعطيل عمداً)
                                                                      │ ينشر payment.completed
                                                                      ▼
                                                             طابور RabbitMQ
                                                                      │ استهلاك
                                                                      ▼
                                                     notification-service ──webhook موقَّع──▶ تطبيق السائق (محاكاة)
```

### جدول الخدمات

| الخدمة | المنفذ | الدور |
|---|---|---|
| `web` | **8080** | الواجهة الرسومية (راكب، سائق، لوحة قيادة، غرفة تحكم) + طبقة BFF |
| `gateway` | 3080 (المضيف) ← 3000 (الحاوية) | نمط بوّابة الواجهات (API Gateway): إصدار/التحقق من JWT، تحديد معدّل الطلبات، توجيه `/trips*` إلى trip-service |
| `trip-service` | 3001 | REST بعقدٍ أولاً (OpenAPI v1 بدورة حياة حقيقية، وv2 مجمَّدة للعرض المتعمَّد لكسر العقد)، ونمط صندوق الإرسال (Outbox) للنشر الآمن من الانهيار |
| `fraud-check-service` | 3002 | تبعية متزامنة هشّة — هدف قاطع الدارة (Circuit Breaker) |
| `payment-service` | 3003 | مستهلكٌ لاتزامني: مفتاح عدم تكرار الأثر، إعادة محاولة بتراجع أُسّي، قاطع دارة يدوي، توجيه إلى طابور الرسائل الميتة |
| `notification-service` | 3004 | مستهلكٌ لاتزامني يُطلق Webhook موقَّعاً (HMAC) |
| `monitor` | 4000 | يستطلع نقطة `/metrics` لكل خدمة كل ثانيتين، إضافةً إلى عمق طوابير RabbitMQ |
| `rabbitmq` | 5672 / 15672 | الناقل + واجهة الإدارة (`guest`/`guest`) |

## دورة حياة الرحلة

هذا هو التغيير الأهم الذي أضفناه بعد البناء الأول: الرحلة لم تعد تكتمل فور إنشائها، بل تمرّ بثلاث حالات حقيقية:

**مطلوبة (requested)** ← يطلبها الراكب عبر `POST /v1/trips` ← **مقبولة (accepted)** ← يقبلها سائقٌ عبر `POST /v1/trips/:id/accept` ← **مكتملة (completed)** ← يُنهيها السائق عبر `POST /v1/trips/:id/complete`

**حدث `trip.completed` لا يُطلَق إلا عند الإكمال الفعلي** — لا عند إنشاء الرحلة. هذا يجعل نمط صندوق الإرسال (Outbox) مرتبطاً بتحوّل حالة حقيقي، لا بمجرّد استدعاء HTTP.

### لماذا لا يزال توليد الحمل الآلي يعمل فوراً؟

`chaos/chaos.js generate-trips` (ولوحة التحكم `/control`) يحتاج أن يُنتج حدث `trip.completed` فوراً دون سائق حقيقي، لأن غرضه اختبار الصمود لا محاكاة التجربة. لذلك أضفنا حقل `autoComplete: true` اختياري على `POST /v1/trips` يتخطّى دورة الحياة ويكتمل فوراً — وهذا بالمناسبة **مثال حيّ على تغييرٍ غير كاسر** (شريحة 12: «الإضافة الاختيارية لا تُكسر أحداً فلا تستحقّ إصداراً»): أضفنا الحقل دون أي إصدار جديد، ودون كسر أي سلوك قديم.

## الواجهة الرسومية (GUI)

أربع صفحات، بتصميم موحّد، تتحدّث جميعها بثوانٍ مع الخلفية عبر Server-Sent Events (بث حيّ بلا استطلاع من جهة المتصفح):

### `/` — الراكب
نموذج لطلب رحلة (نقطة انطلاق، وجهة، أجرة)، وهويّة راكب تُولَّد وتُحفَظ في المتصفح (`localStorage`)، وقائمة «رحلاتي» بجدول زمني حيّ من ست مراحل:

**مطلوبة ● مقبولة ● مكتملة ● فحص احتيال ● مدفوعة ● إشعار السائق**

كل مرحلة لاحقة تُحسَم من خدمة مختلفة تماماً — وهذا تجسيدٌ حرفي لفكرة أن رؤية الراكب لرحلته الواحدة هي بذاتها مسألة تكامل: طبقة BFF في خدمة `web` تُراسل trip-service وpayment-service وnotification-service حيّاً لتجمع قصة رحلة واحدة من ثلاث خدمات لا تعرف بعضها.

### `/driver` — السائق
طابور الطلبات الواردة (رحلات بحالة «مطلوبة») بزرّ **قبول**، ولوحة الرحلة النشطة الحالية بزرّ **إنهاء الرحلة**، وسجلّ قصير لآخر الرحلات المُنجَزة.

### `/dashboard` — لوحة القيادة
نسخة مُعاد تصميمها من مقاييس `monitor`: بطاقة لكل خدمة، أرقامٌ كبيرة للمقاييس المهمّة، حالة قاطع الدارة كشارة ملوّنة، وعمق طوابير RabbitMQ حيّاً — تطبيقٌ مباشر لمبدأ «راقب الوصلة لا الطرفين فقط» (شريحة 17).

**ملاحظة لغوية مقصودة:** أسماء حقول المقاييس (مثل `tripsCreated`، `breakerOpens`) تُركَت بالإنجليزية ومن اليسار إلى اليمين عمداً — فهي أسماء حقول فعلية في استجابة كل خدمة، وتحتاجها عند كتابة تقريرك لتُشير إليها بدقّة في الكود.

### `/control` — غرفة التحكم
كل أمر من أوامر `chaos/chaos.js` كزرّ: إيقاف/استئناف مستهلك، تكرار التسليم، إيقاف/إبطاء `fraud-check-service`، توليد حمل. استخدمها لتشغيل التجارب أدناه بالنقر بدل الكتابة.

## كيف تُشغّل المشروع

```bash
docker compose up --build
```

ثم افتح **http://localhost:8080** — ابدأ من هناك. سطر الأوامر لا يزال يعمل أيضاً للتشغيل الآلي القابل للتكرار:

```bash
npm install                              # مرّة واحدة فقط
node chaos/chaos.js generate-trips 5     # ينشئ 5 رحلات مكتملة فوراً
node chaos/chaos.js status               # يعرض مقاييس كل خدمة حيّاً
```

## التجارب العملية (بحث المتطلب العملي، شريحة 19)

المطلوب في المحاضرة: اختيار بُعدٍ واحد (عقد · تزامن · صمود · معيار · إصدارات)، وبناء تجربة تُعطِّل الطرف الآخر عمداً، وقياس ما يحدث للمعطيات بهدفٍ قابل للقياس. بنينا دعماً كاملاً للأبعاد الخمسة جميعها في `docs/dimensions/`، والصمود هو البُعد الرئيسي (لأنه نفس مثال الشريحة بالضبط: طابور، إيقاف مستهلك، تكرار رسائل عمداً):

- **`resilience-experiment.md`** — إيقاف مستهلك، تكرار رسائل عمداً، قياس الفقد والتكرار المزدوج قبل الضوابط وبعدها.
- **`synchrony.md`** — مقارنة الوصلة المتزامنة الوحيدة في النظام بالوصلات اللاتزامنية تحت نفس العطل.
- **`contract-and-versioning.md`** — إثبات أن اختبار العقد يكشف كسراً في الواجهة قبل وصوله لمستهلك حقيقي.
- **`standards.md`** — ما الذي وفّرته معايير مثل OpenAPI/AsyncAPI/JWT مقارنةً بصيغة مخصّصة.

**مهم:** الفراغات (`___`) في هذه الملفات هي لأرقامك أنت بعد تشغيل التجربة بنفسك — هذا هو الواجب الفعلي. النظام يُعطيك أداة تُنتج أرقاماً حقيقية عند الطلب؛ التقرير والنقاش حولها لك أنت.
